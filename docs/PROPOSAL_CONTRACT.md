# External Schema Proposal Contract — Versions 1.0 & 1.1

Obsidian Property Studio contains **no required AI**. However, it provides a dedicated human-in-the-loop review workspace that can import schema proposals generated by external agents or skills (such as the companion `obsidian-property-advisor` skill packaged with this release).

A proposal is **advisory, untrusted input**. Property Studio validates it locally against strict JSON schemas, compares it with your actual vault inventory, and presents it to you to **Accept as Named Schema**, **Edit in Designer**, **Reconcile with Note**, or **Reject**. A proposal can never modify your vault—the core application has zero vault-mutation capability.

---

## 1. Supported Contract Versions

The application supports two version standards with 100% backward and forward compatibility:

* **Proposal Contract 1.0:** The immutable production baseline.
* **Proposal Contract 1.1:** An additive superset introducing PKM advisory context (`management_purpose`, `source_context`, `target_note_kind`, `proposal_notes`, `schema_target`).

---

## 2. Proposal Payload Format

### Contract 1.1 Example

```json
{
  "proposal_version": "1.1",
  "schema_name": "equipment",
  "description": "Equipment asset and maintenance tracking schema",
  "management_purpose": "Track physical lab equipment, warranties, and maintenance dates",
  "source_context": "Laboratory asset inventory audit",
  "target_note_kind": "equipment",
  "proposal_notes": "Recommend standardizing date formats to ISO-8601 YYYY-MM-DD",
  "schema_target": "Assets/Equipment",
  "generated_by": "obsidian-property-advisor",
  "properties": [
    {
      "name": "serial_number",
      "storage_type": "text",
      "ui_control": "plain",
      "required": true,
      "reason": "Unique identifier assigned by manufacturer",
      "allowed_values": null,
      "confidence": 0.95
    },
    {
      "name": "status",
      "storage_type": "text",
      "ui_control": "single_choice",
      "required": true,
      "reason": "Current operational status of the equipment",
      "allowed_values": ["operational", "maintenance", "retired"],
      "confidence": 0.90
    },
    {
      "name": "project",
      "storage_type": "text",
      "ui_control": "note_link",
      "required": false,
      "reason": "Link to associated project note",
      "allowed_values": null,
      "confidence": 0.85
    }
  ]
}
```

## 3. Top-Level Fields Specification

| Field | Required | Version | Type | Rules & Semantics |
|---|---|---|---|---|
| `proposal_version` | **Yes** | 1.0 & 1.1 | `string` | Exactly `"1.0"` or `"1.1"`. Any other version is rejected fail-closed. |
| `schema_name` | **Yes** | 1.0 & 1.1 | `string` | Non-empty identifier for the schema. |
| `properties` | **Yes** | 1.0 & 1.1 | `array` | Non-empty list of property objects. |
| `description` | No | 1.0 & 1.1 | `string` | Free text describing the overall schema purpose. |
| `generated_by` | No | 1.0 & 1.1 | `string` | Identifier of the producer (model, agent, or skill). |
| `provenance` | No | 1.0 & 1.1 | `string | object` | Provenance metadata preserved and displayed in UI review. |
| `notes` | No | 1.0 & 1.1 | `string` | General free-text notes. |
| `management_purpose` | No | **1.1 only** | `string` | High-level PKM objective (ignored with warning in 1.0). |
| `source_context` | No | **1.1 only** | `string` | Originating document or conversation context (ignored with warning in 1.0). |
| `target_note_kind` | No | **1.1 only** | `string` | Classification of target notes (e.g. `project`, `meeting`, `equipment`). |
| `proposal_notes` | No | **1.1 only** | `string` | Specific advisory advice, caveats, or trade-offs. |
| `schema_target` | No | **1.1 only** | `string` | Target folder scope path or existing Named Schema ID to update. |

## 4. Property Fields Specification

Property object definitions are identical across Contract 1.0 and Contract 1.1:

| Field | Required | Type | Validation Rules |
|---|---|---|---|
| `name` | **Yes** | `string` | Non-empty string; unique within the proposal. |
| `storage_type` | **Yes** | `string` | One of Obsidian's canonical types: `text`, `list`, `number`, `checkbox`, `date`, `datetime`, `tags`. |
| `ui_control` | No | `string` | Default is `plain`. One of: `plain`, `single_choice`, `multi_choice`, `note_link`, `note_link_list`. Must be compatible with `storage_type`. |
| `required` | No | `boolean` | Default is `false`. |
| `reason` | No | `string` | Human-readable explanation of why the property exists. |
| `allowed_values` | No | `array | null` | List of scalar strings/numbers. **Required** if `ui_control` is `single_choice` or `multi_choice`. |
| `confidence` | No | `number | null` | Optional float between `0.0` and `1.0`. |
| `evidence` | No | `any` | Preserved and displayed in provenance review. |
| `provenance` | No | `any` | Preserved and displayed in provenance review. |

### UI Control to Storage Type Compatibility Matrix

| UI Control (`ui_control`) | Allowed Storage Types (`storage_type`) | Output YAML Frontmatter Representation |
|---|---|---|
| `plain` | `text`, `list`, `number`, `checkbox`, `date`, `datetime`, `tags` | Direct value matching storage type |
| `single_choice` | `text`, `number`, `date`, `datetime` | Single scalar value |
| `multi_choice` | `list`, `tags` | YAML list of scalars |
| `note_link` | `text` | Wikilink string `"[[Target Note]]"` |
| `note_link_list` | `list` | List of Wikilinks `["[[Note A]]", "[[Note B]]"]` |

## 5. Rejection & Validation Behavior

A proposal is rejected with structured, actionable error messages when:
* Payload is not valid JSON or not a JSON object.
* `proposal_version` is missing, malformed, or not `"1.0"` or `"1.1"`.
* `schema_name` is missing or empty.
* `properties` is missing, empty, or not a list.
* Any property has a blank or duplicate `name`.
* `storage_type` is not an Obsidian property type (e.g. `"select"` is rejected because it is a UI control, not a storage type).
* `ui_control` is incompatible with `storage_type` according to the compatibility matrix.
* A choice control (`single_choice` or `multi_choice`) does not supply `allowed_values`.

When validation fails:
* Zero state is imported or saved.
* Your Vault is 100% untouched.

---

## 6. Review Workflow in Obsidian Property Studio

When a valid proposal is imported:
1. **Inventory Comparison:** Each proposed property is compared against your active Vault inventory (`new`, `exact_existing`, `case_variant_exists`, or `possible_overlap`).
2. **Current Usage Display:** If a property already exists in your vault, its usage count, dominant storage type, and top observed values are displayed for context.
3. **Provenance Inspection:** Advisory reasons, confidence scores, and management purposes are surfaced cleanly in the UI.
4. **Human Action Decisions:**
   - **Save as Named Schema:** Save directly into your local Named Schema Library with versioning.
   - **Adopt in Designer:** Open in Schema Designer for interactive modifications.
   - **Reconcile with Note:** Test the proposed schema against any note in Note Workspace.
   - **Reject:** Discard the proposal with zero residual side effects.
