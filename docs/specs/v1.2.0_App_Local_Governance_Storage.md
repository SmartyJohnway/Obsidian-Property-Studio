# Architecture Specification — App-Local Governance Storage, Migration & Concurrency

**Document status:** Approved Architecture Freeze (M015)
**Target release:** v1.2.0
**Scope tier:** P0 (REQ-051)
**Primary invariant:** The selected Obsidian Vault is strictly an untrusted, byte-for-byte read-only input source. All governance state must reside in application-local storage outside the Vault.

---

## 1. Storage Location & Directory Resolution

### 1.1 Base Directory Resolution Hierarchy
The application determines its governance storage root via the following resolution hierarchy:

```text
1. Environment Variable: PROPERTY_STUDIO_STORAGE_DIR (if explicitly set, e.g. during testing)
2. Windows Platform Default: %APPDATA%\ObsidianPropertyStudio\
3. Cross-Platform / Fallback: ~/.property_studio/
```

### 1.2 Layout & File Inventory
The storage root is organized into structured JSON entities:

```text
%APPDATA%/ObsidianPropertyStudio/
  ├── config/
  │   └── preferences.json                  # UI theme, locale, window preferences
  ├── glossary/
  │   └── user_glossary.json                # User Property Glossary overrides (REQ-041)
  ├── schemas/
  │   └── named_schemas.json                # Named Schema Library definitions (REQ-042)
  ├── scope_profiles/
  │   └── scope_expected_schemas.json       # Scope → Expected Schema assignments (REQ-044)
  ├── saved_checks/
  │   └── saved_relationship_checks.json    # User-defined Saved Relationship Checks (REQ-033)
  └── backups/
      └── backup_{entity}_{iso_timestamp}_{uuid_short}.json # Collision-safe automatic snapshots
```

## 2. Legacy State Migration Strategy (v1.1.0 → v1.2.0)

In v1.1.0, user preferences and Saved Relationship Checks were persisted in browser `localStorage`:
- `property_studio_locale` (`"zh-Hant"` or `"en"`)
- `property_studio_theme` (`"light"` or `"dark"`)
- `property_studio_saved_checks` (JSON array of saved relationship checks)

### 2.1 Explicit Migration Rules
1. **No Silent Discard:** On startup, the UI checks if legacy `localStorage` keys exist and whether the backend app-local storage has initialized them.
2. **Idempotent Migration:** If backend storage is empty or uninitialized, the frontend transmits legacy state to `/api/storage/migrate_legacy`. The endpoint validates the payload and writes it to app-local files without re-migrating on subsequent launches.
3. **Validate Before Persistence:** Legacy checks are validated against `SavedCheck` schema before persisting.
4. **Preserve Legacy State until Confirmed:** `localStorage` data is preserved until the backend migration returns an explicit `HTTP 200 OK` with validated read-back proof.
5. **Fail-Closed on Corruption:** If legacy `localStorage` data contains malformed JSON or corrupted schemas, the migration engine logs a structured diagnostic warning, leaves the corrupted data in localStorage for user inspection, and initializes safe defaults without crashing.

## 3. Concurrency Semantics & Write Protection

While `os.replace` guarantees atomic file-level writes on POSIX and Windows NTFS (preventing partial file writes during power loss), it does not prevent application-level **lost updates** when multiple browser tabs or asynchronous processes interact.

### 3.1 Optimistic Concurrency Control (OCC)
All entity storage wrappers implement Optimistic Concurrency Control with integer revisions and entity ETags:

```json
{
  "format": "property-studio-storage",
  "storage_schema_version": "1.0",
  "entity_type": "named_schemas",
  "revision": 42,
  "etag": "a1b2c3d4e5f67890...",
  "updated_at": "2026-09-03T00:18:37Z",
  "data": { ... }
}
```

### 3.2 Concurrency Rules
1. **Read:** Reads return the payload along with `revision` and `etag`.
2. **Write / Update:** Mutation requests must submit `expected_revision` (or HTTP `If-Match: etag`).
3. **Stale Write Rejection:** If `expected_revision != current_revision`, the storage engine rejects the write with `HTTP 409 Conflict` (`ConcurrencyError`), returning the current server state and preventing silent overwrites.
4. **Single-Process Writer Guarantee:** In local desktop operation, the embedded backend maintains an in-memory lock per entity file to serialize concurrent thread writes.

## 4. Collision-Safe Auto-Backup Strategy

Before executing any destructive mutation, import, or batch deletion:
1. **Filename Format:**
   `backups/backup_{entity_type}_{YYYYMMDDTHHMMSSZ}_{short_uuid}.json`
   *Example:* `backup_named_schemas_20260903T001837Z_a1b2c3d4.json`
2. **Collision Invariant:** High-resolution ISO timestamp combined with a random 8-character UUID guarantees uniqueness even under high-frequency automated testing.
3. **Retention Policy:** The system retains the 20 most recent snapshots per entity type, pruning older snapshots automatically.

---

## 5. Vault Isolation Verification & Assertions

1. **Path Containment Assertion:**
   Before any read or write operation, the storage engine asserts:
   $$\text{Path}(\text{StorageDir}) \cap \text{Path}(\text{SelectedVaultDir}) = \emptyset$$
   Specifically, `StorageDir` must not be equal to, a child of, or a parent of `SelectedVaultDir`.
2. **Pre/Post File Manifest Validation:**
   Vault integrity test suites (`tests/test_v11_vault_readonly.py`, `tests/test_v12_readonly.py`) verify $0$ created, $0$ modified, and $0$ deleted files in the Vault across all storage operations.
