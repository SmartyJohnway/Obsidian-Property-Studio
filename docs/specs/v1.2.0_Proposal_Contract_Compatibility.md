# Architecture Specification — Proposal Contract Compatibility & AI Boundary

**Document status:** Approved Architecture Freeze (M015)  
**Target release:** v1.2.0  
**Scope tier:** P0 (REQ-046, REQ-047)  
**Core principle:** AI may advise. Deterministic tooling validates. Human decides. The application never silently writes to the Vault.

---

## 1. Proposal Contract Versioning & Compatibility Strategy

To ensure seamless interoperability between v1.0/v1.1 artifacts, external AI agents, the `obsidian-property-advisor` companion skill, and future schema extensions:

1. **Contract Version Lineage:**
   - `proposal_version: "1.0"`: Baseline contract supported in v1.1.0 and permanently supported in v1.2.0.
   - `proposal_version: "1.1"`: Backward-compatible extension adding advisory context fields (`management_purpose`, `source_context`, `target_note_kind`, `proposal_notes`).
2. **Full Backward Compatibility Rule:**  
   The v1.2.0 Proposal Validator transparently accepts valid `1.0` and `1.1` proposals. Unknown optional fields are preserved in metadata rather than failing validation.
3. **Single Source of Truth:**  
   The JSON Schema specification defined in this document is the authoritative standard for all UI placeholders, unit tests, integration fixtures, documentation, and the `obsidian-property-advisor` skill.

## 3. Proposal Review Comparison & Validation Pipeline

When a proposal is submitted (via paste or JSON file upload):

```text
Paste / Open JSON File
        ↓
1. Deterministic JSON Schema Validation
   (Fail closed on syntax errors / contract violations)
        ↓
2. Vault & Scope Inventory Comparison
   (Check which keys already exist in Scope or Whole Vault)
        ↓
3. Property Glossary Comparison
   (Match against built-in & user glossary for labels, aliases, standard types)
        ↓
4. Named Schema Library Comparison
   (Detect collisions or similarities with existing Named Schemas)
        ↓
5. Render Human-Readable Review Workspace
   (Status per property: Compatible, New, Alias Warning, Type Conflict, Value Conflict)
        ↓
6. Explicit Human Action
   ├── [Accept as Named Schema] → Creates Named Schema in Library
   ├── [Edit Candidate] → Opens candidate property editor
   ├── [Reconcile with Existing Note] → Routes to Note Workspace Reconciliation
   └── [Reject Proposal] → Discards with optional user feedback
```

## 4. Companion Skill Decoupling & Invariants

1. **Zero Runtime Dependency:**  
   The core application contains no LLM bindings, API clients, or dependencies on `skills/obsidian-property-advisor/`.
2. **Deterministic Validation Oracle:**  
   The application validator acts as the ground truth. Test fixtures generated by the Skill are tested against `tests/test_v12_ai_proposal.py`.
3. **Strict Advisory Boundary:**  
   The companion skill must never claim ability to write to the user's Vault directly. It produces Markdown notes and/or Proposal JSON for human review in Property Studio.
