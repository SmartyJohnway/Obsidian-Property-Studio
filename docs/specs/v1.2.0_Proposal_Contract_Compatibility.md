# Architecture Specification — Proposal Contract Compatibility & AI Advisory Boundary

**Document status:** Approved Architecture Freeze (M015)
**Target release:** v1.2.0
**Scope tier:** P0 (REQ-046, REQ-047)
**Core principle:** AI may advise. Deterministic tooling validates. Human decides. The application never silently writes to the Vault.

---

## 1. Immutable Proposal Contract 1.0 (Production v1.1.0 Baseline)

The production v1.1.0 Proposal Contract (`docs/PROPOSAL_CONTRACT.md`, `app/core/proposal.py`, `app/core/model.py`) is an **immutable contract standard**. It must be preserved exactly without breaking changes or property renamings.

### 1.1 Exact Proposal Contract 1.0 Specification

#### Top-Level Fields
| Field | Required | Type | Validation Rules |
|---|---|---|---|
| `proposal_version` | **Yes** | `string` | Exactly `"1.0"`. |
| `schema_name` | **Yes** | `string` | Non-empty string. |
| `properties` | **Yes** | `array` | Non-empty array of property objects. |
| `description` | No | `string` | Free text describing the schema purpose (default `""`). |
| `generated_by` | No | `string` | Identifier of the producer/model/agent (default `null`). |
| `provenance` | No | `string \| object` | Provenance information (default `null`). |
| `notes` | No | `string` | Free-text advisory notes (default `null`). |

*Unknown top-level fields are preserved in warnings and never cause validation crashes.*

#### Property-Level Fields
| Field | Required | Type | Validation Rules |
|---|---|---|---|
| `name` | **Yes** | `string` | Non-empty string, unique within the proposal. Valid canonical property key. |
| `storage_type` | **Yes** | `string` | Exactly one of: `text`, `list`, `number`, `checkbox`, `date`, `datetime`, `tags`. (Note: `select` is a UI control, NOT a storage type). |
| `ui_control` | No | `string` | Exactly one of: `plain`, `single_choice`, `multi_choice`, `note_link`, `note_link_list`. Default is `"plain"`. *(DO NOT rename to `control`)*. |
| `required` | No | `boolean` | `true` or `false`. Default is `false`. |
| `reason` | No | `string` | Explanation of why this property exists for PKM management. |
| `allowed_values` | No | `array \| null` | `null` or a list of scalars (`string`, `number`). Required if `ui_control` is `single_choice` or `multi_choice`. |
| `confidence` | No | `number \| null` | `null` or float in range `[0.0, 1.0]`. |
| `evidence` | No | `any` | Preserved and displayed in provenance review. |
| `provenance` | No | `any` | Preserved and displayed in provenance review. |

#### Exact `ui_control` → Allowed `storage_type` Compatibility Matrix
| UI Control (`ui_control`) | Allowed Storage Types (`storage_type`) | Obsidian Frontmatter Serialization |
|---|---|---|
| `plain` | `text`, `list`, `number`, `checkbox`, `date`, `datetime`, `tags` | Raw value matching storage type |
| `single_choice` | `text`, `number`, `date`, `datetime` | Single scalar value |
| `multi_choice` | `list`, `tags` | YAML list of scalars |
| `note_link` | `text` | `"[[Note Name]]"` |
| `note_link_list` | `list` | `["[[Note A]]", "[[Note B]]"]` |

## 2. Additive Proposal Contract 1.1 (v1.2.0 Extension)

To support richer AI advisory context without breaking any existing v1.0 proposals or test fixtures, v1.2.0 introduces **Proposal Contract 1.1** as a strict **additive superset** of Contract 1.0.

### 2.1 Additive Top-Level Advisory Fields in 1.1
When `proposal_version` is set to `"1.1"`, the following optional fields are formally recognized and surfaced in the UI review workspace:

| Field | Required | Type | Advisory Purpose |
|---|---|---|---|
| `management_purpose` | No | `string` | High-level PKM intent (e.g. "Equipment procurement & maintenance tracking"). |
| `source_context` | No | `string` | Context of source document, conversation topic, or project domain. |
| `target_note_kind` | No | `string` | Target classification (e.g. `project`, `equipment`, `regulation`, `meeting`). |
| `proposal_notes` | No | `string` | Advisory suggestions, caveats, or trade-offs for human consideration. |
| `schema_target` | No | `string` | Intended Scope path or target Named Schema identifier. |

*All property-level fields and validation rules in 1.1 remain 100% identical to 1.0.*

## 3. Version Ingestion & Compatibility Strategy

```text
Incoming Proposal Payload
           │
           ├── proposal_version == "1.0" ──► Validated against Contract 1.0 (Accepted unchanged)
           │
           ├── proposal_version == "1.1" ──► Validated against Contract 1.1 (Accepted with additive metadata)
           │
           └── Other / Missing ────────────► FAIL CLOSED with structured error:
                                              "Unsupported proposal_version '...'. Supported: 1.0, 1.1."
```

### 3.1 Strict Invariants
1. **v1.0 Fixture Guarantee:** Existing test fixtures (`fixtures/proposals/valid_equipment.json`) and existing v1.0 proposals must validate with zero errors in v1.2.0.
2. **Single Source of Truth:** The JSON Schema below is the authoritative standard for:
   - UI example placeholders (`app/ui/`)
   - Integration test fixtures (`tests/test_v12_ai_proposal.py`)
   - Documentation (`docs/PROPOSAL_CONTRACT.md`)
   - Companion Skill (`skills/obsidian-property-advisor/`)

## 5. UI Proposal Review & Human Decision Actions

In v1.2.0 (REQ-046), when a proposal is imported, the UI renders a comprehensive **Proposal Review Workspace** rather than ending in raw JSON.

### 5.1 Deterministic Property Comparison Categories
Each proposed property is categorized against current Scope, Whole Vault, Property Glossary, and Schema Library:
1. `✓ Compatible Existing Property`: Matches existing vault/scope key with identical dominant storage type.
2. `＋ New Property`: Canonical key does not exist in vault or glossary.
3. `⚠ Type Conflict`: Proposed `storage_type` differs from vault dominant type (e.g. proposed `list` vs vault `text`).
4. `⚠ Value Vocabulary Conflict`: Proposed `allowed_values` conflict with existing observed values.
5. `ℹ Potential Duplicate / Alias`: Matches an alias in the User Property Glossary.

### 5.2 Explicit Decision Actions
- **`[Accept as Named Schema]`**: Saves proposed schema into Named Schema Library with metadata (`generated_by`, `management_purpose`).
- **`[Edit Candidate]`**: Opens proposed properties in interactive Schema Designer for customization before adopting.
- **`[Reconcile with Existing Note]`**: Routes proposal candidate directly into Note Workspace Reconciliation against a target note.
- **`[Reject Proposal]`**: Explicit terminal dismissal action with optional discard log.

## 6. Companion Skill Contract & Decoupled Boundary

1. **Independent Execution:** The `obsidian-property-advisor` skill lives in `skills/obsidian-property-advisor/` and runs entirely within the AI client runtime.
2. **Zero Core Dependency:** The Property Studio application has no network clients, LLM dependencies, or API key requirements.
3. **Structured Proposal Output:** When generating schema recommendations, the Skill must output JSON conforming strictly to Contract 1.0 or 1.1.
